# NAMING ISSUES

## Overview

This document identifies specific naming problems that reduce code clarity and maintainability.

---

## AMBIGUOUS NAMES

### 1. Generic Type Names

**Issue:** Names that don't convey purpose

**Occurrences:**
```kotlin
// "data" - too generic
val data: String  // What kind of data?

// "result" - unclear
val result: Any  // Result of what?

// "response" - vague
val response: Response  // Response from where?
```

**Recommendations:**
```kotlin
// Be specific
val searchResultData: String
val researchCompletionResult: ResearchResult
val tavilySearchResponse: TavilyResponse
```

---

### 2. Boolean Variable Names

**Issue:** Unclear boolean names

**Occurrences:**
```kotlin
// Unclear
val flag: Boolean
val status: Boolean
val ready: Boolean

// Better
val isProcessing: Boolean
val hasError: Boolean
val isReady: Boolean
```

**Found in Codebase:**
```kotlin
// Check these specific instances
val isChatMode: Boolean  // Good
val isProcessing: Boolean  // Good
val isLoading: Boolean  // Good
// Verify no "flag" or "status" booleans exist
```

---

### 3. Abbreviated Names

**Issue:** Over-abbreviated names reduce clarity

**Occurrences:**
```kotlin
// Unclear abbreviations
val ctx: Context  // Use "context"
val cfg: Configuration  // Use "config"
val req: Request  // Use "request"
val resp: Response  // Use "response"
val msg: Message  // Use "message"
val id: String  // Acceptable (widely understood)
```

**Found in Codebase:**
```kotlin
// Check for these patterns
val ctx = applicationContext  // Rename to context
val cfg = configuration  // Rename to config
```

---

### 4. Single Letter Variables

**Issue:** Single letter names in complex code

**Occurrences:**
```kotlin
// Acceptable in simple loops
for (i in 0..10) { ... }
for (item in list) { ... }

// Problematic in complex logic
val x = calculate(a, b, c)  // What is x?
val t = timeout  // What is t?
```

**Recommendations:**
```kotlin
val result = calculate(param1, param2, param3)
val timeoutMs = 5000
```

## MISLEADING NAMES

### 1. Names That Don't Match Purpose

**Issue:** Name suggests different functionality

**Occurrences:**
```kotlin
// Function named "get" but modifies state
fun getData()  // Actually fetches from network and updates cache

// Class named "Manager" but doesn't manage
class DataManager  // Just passes data through

// Variable named "cache" but isn't cached
val cache = computeExpensiveValue()  // Computed every time
```

**Found in Codebase:**
```kotlin
// Verify these match their purpose
class LazyDecompressor  // Is it actually lazy?
class ActiveSessionManager  // Does it manage or just track?
class ThinkingStorageManager  // Storage or manager?
```

---

### 2. Temporal Coupling in Names

**Issue:** Names that imply wrong timing

**Occurrences:**
```kotlin
// "will" names that don't guarantee
fun willProcess()  // Actually processes immediately

// "should" names
fun shouldSave()  // Actually saves
```

**Recommendations:**
```kotlin
// Be direct about what happens
fun process()
fun save()
```

---

### 3. Type in Name

**Issue:** Including type in variable name

**Occurrences:**
```kotlin
// Redundant type info
val userList: List<User>  // "List" is redundant
val nameString: String  // "String" is redundant
val countInt: Int  // "Int" is redundant

// Better
val users: List<User>
val name: String
val count: Int
```

## INCONSISTENT NAMING PATTERNS

### 1. Verb Tense Inconsistency

**Issue:** Mixed verb tenses

**Occurrences:**
```kotlin
// Present tense
fun processRequest()
fun handleEvent()

// Past tense (inconsistent)
fun requestProcessed()  // Should be processRequest
fun eventHandled()  // Should be handleEvent

// Gerund (inconsistent)
fun processingRequest()  // Should be processRequest
```

**Found in Codebase - Check:**
```kotlin
// Functions starting with different tenses
fun startResearch()  // Present
fun researchStarted()  // Past - inconsistent
```

---

### 2. Noun Form Inconsistency

**Issue:** Singular vs plural inconsistency

**Occurrences:**
```kotlin
// Singular
val note: List<Note>  // Should be notes

// Plural
val notes: Note  // Should be note

// Inconsistent across similar types
val users: List<User>
val itemList: List<Item>  // Should be items
```

**Found in Codebase - Check:**
```kotlin
// Verify collection names are plural
val notes: List<Note>  // Correct
val categories: List<Category>  // Correct
// Check for violations
```

---

### 3. Prefix Inconsistency

**Issue:** Inconsistent use of prefixes

**Occurrences:**
```kotlin
// "get" prefix
fun getNotes()
fun fetchNotes()  // Inconsistent
fun retrieveNotes()  // Inconsistent

// "is/has" prefix
fun isActive()
fun hasActive()  // Different meaning but similar pattern
```

**Recommendations:**
```kotlin
// Standardize prefixes
// Use "get" for simple access
fun getNotes()

// Use "fetch" for remote operations
fun fetchNotesFromServer()

// Use "load" for database operations
fun loadNotesFromDatabase()
```

## DOMAIN-SPECIFIC NAMING

### 1. Agent Terminology

**Issue:** Unclear agent-related names

**Occurrences:**
```kotlin
// What's the difference?
ServerAgent
DeepResearchAgent
AdvancedDeepResearchAgent

// Unclear relationships
class AgentTracer
class AgentPersistenceManager
class AgentPrompts
```

**Recommendations:**
```kotlin
// Be more specific
class ChatAgent  // Instead of ServerAgent
class ResearchAgent  // Instead of DeepResearchAgent
class AdvancedResearchAgent  // Instead of AdvancedDeepResearchAgent

// Clarify supporting classes
class AgentExecutionTracer
class AgentStatePersistence
class AgentPromptTemplates
```

---

### 2. Research Terminology

**Issue:** Research-specific terms may be unclear

**Occurrences:**
```kotlin
// Unclear without context
val achMatrix: AchMatrix  // What is ACH?
val alcoaVerified: Boolean  // What is ALCOA?
val blufSummary: String  // What is BLUF?
```

**Recommendations:**
```kotlin
// Either use full names or add comments
val analysisOfCompetingHypotheses: HypothesisMatrix
// Or keep abbreviation but document
/**
 * ACH: Analysis of Competing Hypotheses
 */
val achMatrix: AchMatrix
```

## FILE NAMING ISSUES

### 1. File vs. Class Name Mismatch

**Issue:** File name doesn't match primary class

**Occurrences:**
```kotlin
// File: DataModels.kt
data class Note(...)  // Should be Note.kt
data class Chat(...)  // Should be Chat.kt

// File: Utils.kt
object StringUtils  // Acceptable for utility collections
```

**Recommendations:**
```kotlin
// One public class per file, matching filename
// File: Note.kt
data class Note(...)
```

---

### 2. Suffix Inconsistency

**Issue:** Inconsistent file suffixes

**Occurrences:**
```kotlin
// ViewModel suffix
SmartyViewModel
ChatViewModel

// No suffix (check for)
class Smarty  // Should be SmartyViewModel or SmartyScreen

// Inconsistent
class NoteRepository  // Has suffix
class Notes  // No suffix - what is this?
```

## NAMING GUIDELINES

### General Rules

1. **Be Descriptive**
   - Names should explain purpose
   - Avoid generic terms like "data", "info", "item"

2. **Be Consistent**
   - Use same pattern for similar things
   - Document naming conventions

3. **Be Concise but Clear**
   - Short is good, clear is better
   - Avoid unnecessary abbreviations

4. **Use Domain Language**
   - Use terms from the problem domain
   - Avoid technical jargon in domain code

### Specific Conventions

**Variables:**
- camelCase
- Noun or noun phrase
- Boolean: is/has/can/should prefix

**Functions:**
- camelCase
- Verb or verb phrase
- Be consistent with tense

**Classes:**
- PascalCase
- Noun or noun phrase
- Avoid "Manager", "Helper", "Util" unless truly managing/helping

**Constants:**
- SCREAMING_SNAKE_CASE
- Descriptive names

**Packages:**
- lowercase
- Singular nouns
- Organize by feature

## REFACTORING STRATEGY

### Safe Refactoring

1. **Use IDE Rename**
   - Android Studio: Shift+F6
   - Ensures all references updated

2. **Small Batches**
   - Rename a few things at a time
   - Test after each batch

3. **Document Changes**
   - Update comments
   - Update documentation

### Risky Refactoring

1. **Public APIs**
   - Consider deprecation first
   - `@Deprecated("Use newName instead")`

2. **Serialized Names**
   - Keep @SerialName for compatibility
   - `@SerialName("old_name") val newName: String`

3. **Database Columns**
   - Requires migration
   - Keep old column as alias if possible
