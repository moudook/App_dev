# COMPLEXITY ANALYSIS

## Overview

This document identifies complex code areas, cyclomatic complexity hotspots, and cognitive load concerns.

---

## HIGH COMPLEXITY FILES

### 1. ServerAgent.kt

**File:** `server/src/main/kotlin/com/example/smarty/server/agent/ServerAgent.kt`

**Lines:** 2107

**Complexity Indicators:**
- Large file size (>2000 lines)
- Multiple responsibilities (agent loop, tool execution, RAG, session management)
- Deep nesting in agent loop
- Multiple state variables

**Key Complex Methods:**

```kotlin
suspend fun runInternal(
    query: String,
    sessionId: String,
    history: List<LlmMessage>,
    modelOverride: String?,
    clientTimezone: String?,
    clientTimeMillis: Long?
): String
```

**Complexity Factors:**
- 6 parameters (high cognitive load)
- Multiple nested blocks (RAG, tool loop, error handling)
- State mutations throughout
- Multiple exit points

**Cyclomatic Complexity Estimate:** 25+ (Very High)

**Recommendations:**
1. Extract agent loop to separate class
2. Extract RAG logic to service
3. Extract tool execution to service
4. Use state pattern for agent phases
5. Reduce parameters with context object

## COMPLEX PATTERNS

### 1. Nested Coroutine Scopes

**Pattern:**
```kotlin
viewModelScope.launch {
    withContext(Dispatchers.IO) {
        repository.operation().collect { result ->
            launch {
                nestedOperation(result)
            }
        }
    }
}
```

**Files:** Multiple ViewModel files

**Issue:** Hard to follow execution flow

**Recommendation:** Flatten coroutine structure

---

### 2. Large When Expressions

**Pattern:**
```kotlin
when (event) {
    is AgentEvent.Processing -> { ... }
    is AgentEvent.ToolCall -> { ... }
    is AgentEvent.Result -> { ... }
    is AgentEvent.Command -> { ... }
    is AgentEvent.Error -> { ... }
    is AgentEvent.StateSync -> { ... }
    is AgentEvent.ToolBlocked -> { ... }
}
```

**Files:** ChatRoutes.kt, ChatViewModel.kt

**Issue:** Violates Open/Closed Principle

**Recommendation:** Use polymorphism (visitor pattern)

---

### 3. Long Parameter Lists

**Pattern:**
```kotlin
fun configureRoutes(
    taskRepo: TaskRepository,
    tagRepo: TagRepository,
    notificationRepo: NotificationRepository,
    chatFolderRepo: ChatFolderRepository,
    // More parameters...
)
```

**Files:** Application.kt, Route configuration

**Issue:** Hard to maintain, easy to misorder

**Recommendation:** Use dependency injection container

---

### 4. Magic Numbers

**Pattern:**
```kotlin
private const val TIMEOUT_WARNING_MS = 12 * 60 * 1000L
private const val TIMEOUT_FORCE_COMPLETE_MS = 15 * 60 * 1000L
private const val CONTEXT_THRESHOLD = 8000
private const val MAX_CONCURRENT_SEARCHES = 10
```

**Files:** Agent files

**Issue:** Unclear origin of values

**Recommendation:** Document rationale or make configurable

---

### 5. String Literals

**Pattern:**
```kotlin
val eventType = when(event) {
    is AgentEvent.Processing -> "processing"
    is AgentEvent.ToolCall -> "tool_call"
    is AgentEvent.Result -> "result"
    ...
}
```

**Files:** ChatRoutes.kt

**Issue:** Duplication, typo-prone

**Recommendation:** Use enum or sealed class with serial names

## COMPLEXITY REDUCTION STRATEGIES

### 1. Extract Method

**Before:**
```kotlin
suspend fun runInternal(...) {
    // 500 lines of logic
}
```

**After:**
```kotlin
suspend fun runInternal(...) {
    val context = buildContext(...)
    val history = loadHistory(...)
    val response = executeAgentLoop(context, history)
    return formatResponse(response)
}
```

### 2. Extract Class

**Before:** ServerAgent handles everything

**After:**
```kotlin
class ServerAgent(
    private val ragService: RagService,
    private val toolExecutor: ToolExecutor,
    private val sessionManager: SessionManager,
    private val responseFormatter: ResponseFormatter
)
```

### 3. State Pattern

**Before:**
```kotlin
when (status) {
    ResearchStatus.PLANNING -> plan()
    ResearchStatus.SEARCHING -> search()
    ResearchStatus.ANALYZING -> analyze()
    ...
}
```

**After:**
```kotlin
interface ResearchState {
    fun execute(context: ResearchContext): ResearchState
}

class PlanningState : ResearchState { ... }
class SearchingState : ResearchState { ... }
```

### 4. Builder Pattern

**Before:**
```kotlin
ResearchState(
    id = UUID.randomUUID().toString(),
    topic = topic,
    status = ResearchStatus.PLANNING,
    // 20 more parameters
)
```

**After:**
```kotlin
ResearchState.builder(topic)
    .withInitialStatus(ResearchStatus.PLANNING)
    .withPlan(plan)
    .build()
```
