# INCONSISTENCIES

## Overview

This document identifies inconsistencies in naming, patterns, architecture, and implementation across the codebase.

---

## NAMING INCONSISTENCIES

### 1. Project Name Inconsistency

**Issue:** Project referred to by multiple names

**Occurrences:**
- "Smarty" - README, Android package, most files
- "Friday" - Server Application.kt comment, some internal references
- "Friday Server" - Server startup log

**Files:**
```kotlin
// README.md
# Smarty - Advanced AI Agent

// Application.kt
// Friday Server - Cloud-hosted agent runtime

// build.gradle.kts
rootProject.name = "Friday"
```

**Impact:** Confusion about project identity

**Recommendation:** Standardize on "Smarty" (matches public branding)

---

### 2. Version Number Inconsistency

**Issue:** Different version numbers in different places

**Occurrences:**
- README.md: Version 6.0.0
- app/build.gradle.kts: versionName = "3.2.0"
- server/build.gradle.kts: version = "1.0.0"

**Impact:** Confusion about actual version

**Recommendation:** Align all version numbers, use single source of truth

---

### 3. Repository Naming

**Issue:** Inconsistent repository naming pattern

**Occurrences:**
```kotlin
// Some use "Repository" suffix
NoteRepository
ChatRepository
CalendarRepository

// Some use different patterns
PostgresVectorStore  // Should be VectorStoreRepository?
ConversationSummarizer  // Service or Repository?
```

**Impact:** Unclear categorization

**Recommendation:** Standardize naming convention

---

### 4. Agent Naming

**Issue:** Multiple agent naming patterns

**Occurrences:**
```kotlin
// "Agent" suffix
ServerAgent
DeepResearchAgent
AdvancedDeepResearchAgent

// No suffix but agent-like
OrchestratorService  // Routes requests like an agent
```

**Impact:** Unclear agent vs service distinction

**Recommendation:** Clarify agent vs service responsibilities

---

### 5. Event/Command Naming

**Issue:** Inconsistent event naming

**Occurrences:**
```kotlin
// AgentEvent types
Processing  // Present participle
ToolCall    // Noun
Result      // Noun
Error       // Noun
Command     // Noun
StateSync   // Noun
ToolBlocked // Past participle
```

**Impact:** Minor inconsistency

**Recommendation:** Standardize to one pattern (nouns recommended)

---

## ARCHITECTURAL INCONSISTENCIES

### 1. Dependency Injection Approaches

**Issue:** Multiple DI patterns used

**Occurrences:**
```kotlin
// Manual DI (Server)
val vectorStore = PostgresVectorStore()
val agent = ServerAgent(llmProvider, vectorStore, ...)

// ViewModel Factory (Android)
class SmartyViewModelFactory(...) : ViewModelProvider.Factory

// Direct instantiation (some places)
val repository = NoteRepository(dataSource)
```

**Impact:** Inconsistent patterns, harder to test

**Recommendation:** Choose single DI approach (Hilt/Koin for Android, manual or Koin for server)

---

### 2. Error Handling Approaches

**Issue:** Inconsistent error handling

**Occurrences:**
```kotlin
// Try-catch with logging
try {
    operation()
} catch (e: Exception) {
    logger.error("Failed", e)
    throw e
}

// Try-catch with result
try {
    Result.Success(operation())
} catch (e: Exception) {
    Result.Error(e.message)
}

// No error handling (some places)
operation()  // Exceptions propagate
```

**Impact:** Inconsistent error propagation

**Recommendation:** Standardize error handling pattern

---

### 3. State Management Approaches

**Issue:** Different state management patterns

**Occurrences:**
```kotlin
// StateFlow (most ViewModels)
val state: StateFlow<State> = _state.asStateFlow()

// LiveData (possibly some older code)
val state: LiveData<State>

// MutableState (Compose)
var state by remember { mutableStateOf(...) }
```

**Impact:** Inconsistent reactivity patterns

**Recommendation:** Standardize on StateFlow for ViewModels

---

### 4. Database Access Patterns

**Issue:** Inconsistent database access

**Occurrences:**
```kotlin
// Exposed ORM (Server)
Notes.select { (Notes.userId eq userId) }

// Raw SQL (DatabaseFactory migrations)
stmt.execute("CREATE TABLE ...")

// Room (Android)
noteDao.getAll()
```

**Assessment:** Acceptable - different ORMs for different platforms

---

### 5. API Response Patterns

**Issue:** Inconsistent API response formats

**Occurrences:**
```kotlin
// Success with data
call.respond(HttpStatusCode.OK, data)

// Success with wrapper
call.respond(HttpStatusCode.OK, mapOf("success" to true, "data" to data))

// Error formats
call.respond(HttpStatusCode.InternalServerError, mapOf("error" to "message"))
call.respond(HttpStatusCode.InternalServerError, "Error message")
```

**Impact:** Client parsing complexity

**Recommendation:** Standardize response format

---

## PATTERN INCONSISTENCIES

### 1. Coroutine Scope Usage

**Issue:** Inconsistent coroutine scope usage

**Occurrences:**
```kotlin
// viewModelScope (correct)
viewModelScope.launch { ... }

// lifecycleScope (in Activity)
lifecycleScope.launch { ... }

// Global scope (potential issue)
GlobalScope.launch { ... }  // Check if used
```

**Impact:** Potential memory leaks

**Recommendation:** Audit for GlobalScope usage

---

### 2. Serialization Approaches

**Issue:** Multiple serialization libraries

**Occurrences:**
```kotlin
// Kotlinx Serialization (primary)
@Serializable
data class Note(...)

// Gson (legacy?)
implementation(libs.gson)
```

**Impact:** Larger APK, confusion

**Recommendation:** Migrate fully to Kotlinx Serialization or remove Gson

---

### 3. HTTP Client Usage

**Issue:** Multiple HTTP clients

**Occurrences:**
```kotlin
// Ktor Client (primary)
ktorClient.get("/api/...")

// OkHttp (direct)
okHttpClient.newCall(request).execute()
```

**Impact:** Duplicate functionality

**Recommendation:** Standardize on Ktor Client

---

### 4. Logging Approaches

**Issue:** Inconsistent logging

**Occurrences:**
```kotlin
// SLF4J (Server)
logger.info("Message")

// Android Log (Android)
Log.d("Tag", "Message")

// Timber (not visible but check)
Timber.d("Message")
```

**Assessment:** Acceptable - different platforms have different standards

---

## IMPLEMENTATION INCONSISTENCIES

### 1. Null Handling

**Issue:** Inconsistent null handling

**Occurrences:**
```kotlin
// Safe calls
user?.userId

// Elvis operator
val name = name ?: "Default"

// Force unwrap (potential issue)
repository!!

// Explicit checks
if (user != null) { ... }
```

**Impact:** Potential null pointer exceptions

**Recommendation:** Audit !! usage, standardize on safe calls

---

### 2. String Handling

**Issue:** Inconsistent string handling

**Occurrences:**
```kotlin
// String templates
"Hello $name"

// String concatenation
"Hello " + name

// Multi-line strings
"""
Multi-line
string
"""
```

**Assessment:** Minor - all are valid Kotlin

---

### 3. Collection Operations

**Issue:** Inconsistent collection operations

**Occurrences:**
```kotlin
// Functional style
list.map { ... }.filter { ... }

// Imperative style
for (item in list) {
    // process
}

// Mixed
list.forEach { item ->
    // process
}
```

**Recommendation:** Prefer functional style for transformations

---

### 4. Magic Numbers

**Issue:** Magic numbers in different places

**Occurrences:**
```kotlin
// Defined as constants (good)
private const val MAX_EXECUTION_TIME_MS = 30 * 60 * 1000L

// Inline (bad)
if (query.length > 10000) { ... }
if (results.size > 5) { ... }
```

**Recommendation:** Extract all magic numbers to constants

---
